Le pipeline type : de l'init au destroy

Un même pipeline enchaîne des étapes automatiques (relecture, sans risque) puis des étapes manuelles (elles créent ou détruisent du réel — on met un humain dans la boucle).

stage · setup
init
auto
terraform init -backend-config="key=ec2/$TF_ENV/…"
Configure le backend distant — un state par env.
stage · validate
validate
auto
terraform fmt -check
terraform validate
Lint + « compilation à blanc ». Aucun appel cloud.
stage · plan
plan
auto
terraform plan -var-file=$TF_ENV.tfvars
Pour relecture : ce qui va changer, rien n'est appliqué.
stage · deploy
apply
manuel
terraform apply -auto-approve …
Provisionne l'infra réelle. Gate humain (bouton ▶).
stage · connect
connect / config
manuel
ssh -i key.pem ec2-user@$IP
Vérifie l'accès, configure / provisionne le serveur.
stage · cleanup
destroy
manuel
terraform destroy -auto-approve …
Nettoie tout. L'environnement passe stopped.
auto lancé à chaque push — sûr, ne modifie rien de réel manuel attend un clic — crée, modifie ou détruit des ressources

Secrets, variables & clés SSH

Jamais dans le repo. Ils vivent dans le moteur de pipeline (variables CI/CD chiffrées) ou dans un coffre (Vault). Le job les reçoit en variables d'environnement.

Variable Credentials AWS AWS_ACCESS_KEY_ID / SECRET

Masquées + protégées. Le provider et le backend S3 les lisent tout seuls via l'environnement — aucun access_key dans le code.

Variable SSH_PUBLIC_KEY

Injectée en TF_VAR_ssh_public_key → Terraform crée la aws_key_pair. Rien à pré-créer dans la console.

Filebase64 SSH_PRIVATE_KEY

« Masked » refuse le multi-lignes → on stocke la clé encodée base64 (une ligne). Type File = la variable contient un chemin. Le job décode : base64 -d "$SSH_PRIVATE_KEY" > key.pem puis chmod 600.

Pipeline vs Vault. Pour un lab : variables du moteur CI, simple. En entreprise : OIDC (GitLab s'authentifie à AWS sans secret long terme) ou Vault (secrets à durée de vie courte, audités, révocables).

Un environnement par branche

GitLab exécute déjà un pipeline par branche. On déduit l'environnement de $CI_COMMIT_REF_NAME — même code, seuls le var-file et la clé de state changent.

dev→ TF_ENV=dev → state ec2/dev/terraform.tfstate
EC2 dev · t3.micro
main→ TF_ENV=prod → state ec2/prod/terraform.tfstate
EC2 prod · t3.small
workflow:
  rules:
  - if: '$CI_COMMIT_REF_NAME == "main"'
    variables: { TF_ENV: "prod" }
  - if: '$CI_COMMIT_REF_NAME == "dev"'
    variables: { TF_ENV: "dev" }

Une clé de state par env → pas de destruction croisée. Le bucket est partagé, la clé ne l'est pas : un apply sur dev ne peut pas écraser prod.

4

Variante : un stage deploy, plusieurs jobs cibles

Autre modèle : au lieu d'« une branche = un env », on garde un pipeline avec un stage deploy qui contient un job par cible. On promeut le même code de dev → test → prod, chaque cran plus verrouillé.

deploy-to-dev
Automatique sur chaque push. Bac à sable, feedback rapide.
deploy-to-test
Manuel. Recette / intégration avant de promouvoir.
deploy-to-prod
Manuel + uniquement sur la branche prod, avec approbation.

Chaque job pointe le même code sur un -var-file et une clé de state différents. La cible prod est protégée par un rules: de branche + when: manual (et idéalement un environnement protégé à approbateurs).

Branche = env (isolation forte, un pipeline par env) vs stage deploy multi-jobs (promotion visible dev→test→prod dans un seul pipeline). Les deux coexistent ; on choisit selon le besoin d'isolation et de traçabilité de la promotion.

5

Quoi d'autre ? Les enjeux à ne pas oublier

State & concurrence

  • Backend distant partagé, pas de state local qui traîne
  • Verrou du state (use_lockfile S3 ou DynamoDB) — pas deux apply en même temps
  • resource_group sur apply/destroy : sérialise un même env
  • Une clé de state par env → jamais de destruction croisée

Sécurité

  • Moindre privilège : les creds CI n'ont que ce qu'il faut
  • OIDC > clés statiques ; secrets en coffre (Vault)
  • Secrets jamais dans le repo ni dans les logs
  • SG 0.0.0.0/0 = OK lab, à restreindre en prod

Cycle de vie & coût

  • apply / destroy manuels : rien ne part tout seul
  • auto_stop / TTL : l'env éphémère se nettoie
  • Traquer les ressources orphelines (fuites de coût)
  • On ne paie que ce qu'on utilise

Fiabilité

  • plan = relecture obligatoire avant apply
  • Drift : détecter les modifs faites à la main
  • Idempotence : rejouer donne le même résultat
  • Rollback = ré-appliquer une version ; versions TF/provider épinglées

Exploitation

  • Outputs exposés (IP, URL) → environment.url cliquable
  • Approbations / environnements protégés sur prod
  • Logs & traces des jobs pour l'audit
  • Données persistantes ≠ éphémère → sauvegardes
